# Repositories and branches

## Two mirrored repositories

`drsounds/soarfulness` and `drsounds/aqua-wave-dream` share the same `src/`
almost file for file. On 2026-10-31 aqua-wave-dream PR #219 copied
soarfulness's `src/` wholesale (soarfulness was a strict superset at the
time) and moved assets to `public/apps/`. Since then every feature has been
built as **one PR per repo**, usually from the same branch name, with the
same code.

In practice soarfulness is ahead: most feature PRs are merged there, while
many of their aqua-wave-dream twins are still open. Before mirroring a
change, check whether the feature exists on the target repo's `main`, not
just whether it was "done in both repos". The
[feature index](../reference/feature-index.md) tracks this.

### What is different in aqua-wave-dream

| Area | soarfulness | aqua-wave-dream |
| --- | --- | --- |
| Advanced movement modes | Always available | Hidden behind **EXPERIMENTELLT LÄGE** (`src/lib/experimentalModes.ts`, localStorage `aquafulness:experimentalModes:v1`, off by default). With it off only SIMMARE (`float`) and FARKOST (`watercraft`) are offered, and a guard effect in `index.tsx` forces swing, noclip, bodyflight, `tornadoOn` and `freakOutOn` off. Gate any new advanced-mode UI on `isCameraModeAvailable()` / the experimental flag. |
| EXTREME toggle | Always shown | Shown only in EXPERIMENTELLT LÄGE |
| TORNADO | One shared TORNADO toggle for FRI/GUNGA/FLYG; in BODYFLIGHT it reads VIRVEL | GUNGA's own `swingTornado*` plus a separate VIRVEL camera mode / `bodyflightWhirlpoolOn` |
| Public identity | `src/lib/appLinks.ts` points at soarfulness URLs | aqua URLs, Android id `se.aquafulness.app.gen7`. The "get the app" banner was removed at the owner's request; don't re-add a native-app promo. |
| Lovable asset pointers | `src/assets/*.asset.json` with soarfulness's Lovable project id | Same files, aqua's project id |
| Deploy | Self-hosted deploy on every push to `main` (see [Deployment](deployment.md)) | No deploy workflow; Lovable hosting |
| Login | `/login` route | No `/login` route |
| Lockfile | `bun.lock` (points at a mirror the cloud sandbox can't reach) | `package-lock.json` is out of sync; install with `npm install --no-package-lock` |

Everything outside `src/` and `public/` (Android project, workflows, README)
is maintained separately in each repo.

### Soartify/soarfulness

An older repository, `Soartify/soarfulness`, exists too. Earlier PR numbers in
commit messages and comments (for example "soarfulness #74" for BODYFLIGHT)
can refer to it. It can't be attached to the same cloud session as
`drsounds/soarfulness` because both check out to the same folder name; work
was moved between them with `git format-patch` files.

## Branch and PR rules

- Both repos have a `CLAUDE.md` that says: **whenever you push commits to a
  branch, open a pull request for it** (unless one exists) against `main`.
- Never rewrite published history. Both repos sync with
  [Lovable](https://lovable.dev): force pushes, rebases or squashes of pushed
  commits rewrite history on Lovable's side and lose the project history (see
  `AGENTS.md`). Merge `main` into a branch instead of rebasing it.
- Commits pushed to the connected branch show up in the Lovable editor, so
  keep `main` in a working state.
- One feature = one PR per repo. Name both PRs the same and mention the
  twin PR number in each description.
- `src/routeTree.gen.ts` is regenerated by the dev server. Revert it before
  committing unless you added or removed a route.
- `index.tsx` is not prettier-clean on `main`. Don't run `prettier --write`
  on the whole file; it creates a huge unrelated diff and merge conflicts
  with every open PR.

## Why big PRs merge cleanly (anchor-based patches)

Because `index.tsx` and `SettingsPanel.tsx` are enormous and many PRs touch
them at once, features have been integrated with small **anchor-based patch
scripts**: a script finds a known line (for example the `snowCoverStrength`
lines, the `new Aurora(scene)` line or the VÄRLDSGRÄNS wrap comment) and
inserts the new feature's lines right after it in every list where settings
are enumerated. The same script then applies to both repos. See
[Porting between repos](../guides/porting-between-repos.md).
